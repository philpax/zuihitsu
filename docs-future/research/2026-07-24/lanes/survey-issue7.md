# Convergent-evolution survey, part 2 — current-generation persistent-memory personal agents

Scope: ten actively-developed repositories representing the present wave of "give an LLM a persistent self" projects, surveyed for zuihitsu's ontology redesign (partially discharges issue #7). Sources are READMEs, design docs, and source files fetched directly from each repository's default branch on 2026-07-23, plus one general web search context. Every load-bearing claim below cites the specific file it came from. Where a system's internals were not reachable (private hosted service, doc not present in the repo, code too deep to fetch under this survey's budget), that is stated rather than inferred.

---

## letta-code (github.com/letta-ai/letta-code)

**What it is.** The CLI/desktop harness for Letta (formerly MemGPT) agents — "Letta Code agents have memory, identity, and a sense of experience over time" ([README.md](https://github.com/letta-ai/letta-code/blob/main/README.md)).

1. **Source of truth.** Agent state (memory blocks, conversation history, skills) is server-side in Letta Cloud or a self-hosted Letta server — a mutable object store, not an append-only log as far as the README documents. Distinctively, **all context (including memory blocks) is also tracked via git** ("MemFS"): the README states you can sync context to a custom GitHub repository via `/memory-repository set git@github.com:...`. This makes git history a secondary, human-inspectable audit trail over a primary mutable store, the inverse of zuihitsu's event-log-is-truth model.
2. **Users/identity over time.** Not detailed in the fetched surface (this level of design lives in Letta core, not letta-code, and was out of this survey's fetch budget). letta-code is a harness over Letta's memory-block agent, not itself an identity system.
3. **Memory shape.** Classic MemGPT/Letta **memory blocks** — named, agent-editable text sections (persona, human, etc.) that are always in context — plus **skill learning** (agents write and refine their own skill files) and periodic **`/sleeptime`** dreaming and **`/doctor`** memory-quality audits. Fact shape is prose block, self-edited by the agent via memory-editing tool calls; there is no typed/triple layer visible in this repo.
4. **Scheduling/contact.** "Crons & Schedules" — configurable heartbeats and crons so agents "work across time with self-managed schedules" ([README.md](https://github.com/letta-ai/letta-code/blob/main/README.md)). Detail of the scheduler is not in this repo (likely server-side).
5. **Execution/tool boundary.** Hooks (`hooks/*.sh`), a permissions system with auto-approve/deny lists, and subagents (general-purpose, forked, recall, history-analyzer) callable sync or async, including an agent calling itself as a subagent.
6. **Most distinctive idea.** Treating the agent's entire context — including its self-edited memory blocks — as a **git-versioned filesystem** ("MemFS"). This gives free diffing, rollback, and human review of every self-edit the agent makes to its own memory, a mechanism zuihitsu's event log achieves differently (replay) but does not expose as a diffable artifact.

## pattern (github.com/orual/pattern)

**What it is.** A Rust MemGPT/Letta-style agent platform, dual-purpose as a generic framework and as "Pattern," a multi-agent ADHD-support constellation running live on Bluesky ([README.md](https://github.com/orual/pattern/blob/main/README.md)).

1. **Source of truth.** SQLite via `pattern_db` (migrated *from* SurrealDB, per the README's "Current Status"), with FTS5 full-text and `sqlite-vec` vector search — a mutable relational store, not an append-only log.
2. **Identity over time.** Multi-agent "constellation" with named agents (Pattern, Entropy, Flux, Archive, Momentum, Anchor) each with fixed cognitive roles; a `pattern-current-human-block.md` is the live "who we're talking to" slot, explicitly empty when no one is present ([bsky_agent/pattern-current-human-block.md](https://github.com/orual/pattern/blob/main/bsky_agent/pattern-current-human-block.md)). Multi-user support models one primary "partner" the constellation supports while also interacting with others; no separate identity-merge mechanism was found.
3. **Memory shape.** Three tiers: **core memory blocks** (persona, current human, observations — prose, always in context), **working/archival memory** (searchable, semantic), and — the most structurally distinctive feature — **Loro CRDT-backed typed block schemas**: `Text`, `Map` (typed fields with `FieldType::Number`/`Text`/etc.), `List` (bounded, e.g. tasks), `Log` (append-only with a display limit and structured entry schema: timestamp, agent_id, fields), and `Composite` (named sub-sections, some read-only) ([docs/architecture/memory-and-groups.md](https://github.com/orual/pattern/blob/main/docs/architecture/memory-and-groups.md)). This is a genuine structured-fact layer sitting *above* the prose-block default — closer to zuihitsu's typed-entry ambition than any other system surveyed. Memory also carries a **permission model** per block (ReadOnly / Partner / Human / Append / ReadWrite / Admin), with `Partner`/`Human`-level writes requiring approval through a `PermissionBroker` that surfaces as a Discord/CLI notification.
4. **Scheduling/contact.** The orchestrator "runs background checks every 20-30 minutes for attention drift and physical needs" (README); a "sleeptime context sync" prompt has each agent review a shared `constellation_activity` block, update its own memory, and escalate only if necessary via `send_message` ([bsky_agent/sleeptime-context-sync-prompt.md](https://github.com/orual/pattern/blob/main/bsky_agent/sleeptime-context-sync-prompt.md)) — a two-tier (rules-based + AI) cost-optimized sleeptime design per the README.
5. **Execution/tool boundary.** Typed tool system (README references `docs/architecture/tool-system.md`, not fetched in depth); built-in tools include block, recall, search, send_message, file, shell, web, calculator. Agent groups support coordination patterns (round-robin, dynamic, pipeline, supervisor, voting, sleeptime).
6. **Most distinctive idea.** The **CRDT-backed typed block schema with per-block permissions and human-approval gating**. It is the one system surveyed that gives memory *field types* (`FieldType::Number`, structured log entries) rather than leaving everything as prose, and the one that models "who is allowed to overwrite this fact" as a first-class access-control question rather than an authority tier baked into write paths.

## bound (github.com/bound-agents/bound)

**What it is.** A self-hosted, multi-host-replicated personal agent (Bun/TypeScript monorepo, 12 packages) with a scheduler, a knowledge graph, and a `boundless` terminal coding agent ([README.md](https://github.com/bound-agents/bound/blob/main/README.md), [docs/design/architecture.md](https://github.com/bound-agents/bound/blob/main/docs/design/architecture.md)). Explicitly marked "still very experimental" by its author.

1. **Source of truth.** SQLite, with **all writes to synced tables required to go through a change-log outbox** (`insertRow`/`updateRow`/`softDelete`) — never raw SQL — so that other hosts learn about every change via `change_log` replication ([docs/invariants.md](https://github.com/bound-agents/bound/blob/main/docs/invariants.md), invariant 1). Soft deletes only (invariant 2). This is architecturally the closest of the ten to zuihitsu's own discipline (a single writer path, replicated via events) but the *rows themselves* are still mutable key-value/edge records, not immutable append-only facts — the change-log is a sync mechanism, not the source of truth for what is currently believed.
2. **Identity.** Users are managed via an operator-curated `allowlist.json` (a default web user plus a user→platform-handle map); a `connector_handles` synced table exists but this survey did not find a same_as/merge mechanism or a per-platform-stub model as rich as zuihitsu's.
3. **Memory shape.** `semantic_memory` is a **flat key-value store** (`memorize --key ... --value ...`), not prose entries — closer to a fact-per-key model. It gained, over three RFCs the repo tracks explicitly:
   - **Tiered retrieval** (pinned / hierarchical) because at 700+ entries, keyword+graph retrieval surfaced only ~4% of memory per turn ([docs/design/specs/2026-04-10-hierarchical-memory.md](https://github.com/bound-agents/bound/blob/main/docs/design/specs/2026-04-10-hierarchical-memory.md)). Notably, this RFC's amendment (2026-05-26) *removed* a redundant "pin by key-prefix OR by tier column" mechanism once the schema-level `tier` column fully replaced it — a real-world instance of exactly the "two authorities for one concept" failure zuihitsu is trying to design away from at the ontology level.
   - **A `memory_edges` graph** with a canonical, closed 10-relation vocabulary (`related_to, informs, supports, extends, complements, contrasts-with, competes-with, cites, summarizes, synthesizes`), enforced by a **database trigger** plus agent-layer pre-flight validation, with a `context TEXT` column added specifically to carry bespoke phrasing that used to be smuggled into the relation field, and a startup-time idempotent normalization migration that collapses spelling variants and merges resulting duplicate edges deterministically ([docs/design/specs/2026-04-20-edge-graph-normalization.md](https://github.com/bound-agents/bound/blob/main/docs/design/specs/2026-04-20-edge-graph-normalization.md)). This is close to a live case study of zuihitsu's failure #3/#6 (bare edges, agent-coined vocabulary drift, immutable schema) — bound hit the *identical* problem (78% of edges were one-off free-text relations) and resolved it with a closed enum plus a free-text side-channel, exactly the "recognised closed sets ride as enums" principle in zuihitsu's own CONTRIBUTING.md.
   - A **memory-delta injection** mechanism so that a thread sees what changed in semantic memory since its own last turn (not just a raw count), including a tombstone-aware "`{key}: [forgotten]`" delta line for retracted facts, with a well-specified baseline-selection fallback chain per context type ([docs/design/specs/2026-03-29-memory-visibility.md](https://github.com/bound-agents/bound/blob/main/docs/design/specs/2026-03-29-memory-visibility.md)). This addresses a class of problem zuihitsu has not designed for: cross-thread staleness when memory changes out-of-band (a scheduled task writes a fact that an unrelated live conversation has no signal about).
4. **Scheduling/contact.** A first-class **heartbeat task type** distinct from cron/deferred/event tasks: clock-aligned interval math (not cron expressions), a `buildHeartbeatContext()` that assembles standing instructions (itself stored as a `semantic_memory` key), pending advisories, recent task outcomes, and per-thread activity at *runtime* rather than replaying a static payload; quiescence-aware interval stretching (a 30-min interval becomes 2.5h after 4h idle); a persistent thread giving the heartbeat memory of its own past checks ([docs/design/specs/2026-04-04-heartbeat-task.md](https://github.com/bound-agents/bound/blob/main/docs/design/specs/2026-04-04-heartbeat-task.md)).
5. **Execution/tool boundary.** A write-confinement sandbox for `boundless` (seatbelt/bubblewrap/IsolationSession per OS), a store-and-forward relay protocol for cross-host tool calls/inference/delegation, and an explicit invariant that tool-message persistence must happen immediately after each tool call, before the next LLM call (invariant 7) — a lesson learned from context drift and duplicate tool calls in production.
6. **Most distinctive idea.** The **edge-graph canonicalization RFC** is the single most directly relevant artifact in this whole survey: an independently-arrived-at instance of zuihitsu's failure class #3/#6 (bare, agent-coined, immutable relation vocabulary), solved with a closed enum + `context` free-text escape hatch + deterministic startup normalization + trigger-level enforcement. It is evidence the failure is real and general, not a zuihitsu-specific implementation slip, and it demonstrates one concrete fix shape (context column) that zuihitsu doesn't currently have.

## Alpha-dotclaude (github.com/Pondsiders/Alpha-dotclaude)

**What it is.** A personal Claude Code character configuration (not a framework) — "Alpha," a persistent identity built from a durable-facts layer plus a diary, driven entirely by markdown context files and slash-command skills ([agents/Alpha.md](https://github.com/Pondsiders/Alpha-dotclaude/blob/main/agents/Alpha.md)). The memory *store* itself (an MCP server called "Cortex," referenced as `mcp__cortex__store_memory` / `mcp__cortex__add_to_diary`) is external and not in this repository — this survey could not inspect its internals.
1. **Source of truth.** Plain markdown files under `~/.claude/alpha/context/*.md`, assembled into context by a generator script (`generate_alpha_context.py`) invoked at session start and after `/finish` ([skills/alpha_context/SKILL.md](https://github.com/Pondsiders/Alpha-dotclaude/blob/main/skills/alpha_context/SKILL.md)). Each file is capped at 30,000 chars and stamped with a provenance header. The actual memory/diary store (Cortex) is opaque to this survey.
2. **Identity over time.** A single fixed persona (no multi-user/participant model visible); identity content is split explicitly into a **durable layer** ("who you are, steady across sessions, kept true by deliberate edit") versus a **diary** ("the letter past-you leaves tomorrow-you") — an operator-legible two-tier distinction between standing self-facts and episodic narrative that maps loosely onto zuihitsu's asserted/occurred split, but for *self*-facts rather than facts-about-others.
3. **Memory shape.** Prose files, no structure beyond markdown headings and a glob-ordered concatenation. No triples, no visibility postures found.
4. **Scheduling/contact.** Not evident in this repo (session-driven only — `/start`, `/continue`, `/finish`, `/handoff` skills for context-window boundaries, not calendar-driven wake-ups).
5. **Execution/tool boundary.** Ordinary Claude Code tool/skill/hook model; a `handoff` skill formalizes a **mid-session context-window swap ritual**, distinct from end-of-day `/finish`: "when you finish, you tell the story of the day. When you handoff, you tell the story of the day so far" ([skills/handoff/SKILL.md](https://github.com/Pondsiders/Alpha-dotclaude/blob/main/skills/handoff/SKILL.md)).
6. **Most distinctive idea.** The **explicit durable-vs-diary split with a stated audience and register for each** ("past-you leaves notes for future-you," read the constitution "like you wrote it, because you did") — and the **handoff/finish distinction**, which recognizes that a context-window boundary and a day boundary are two different discontinuities requiring two different memory-writing registers (immediate continuation vs. emotional narrative closure). This is a UX/pedagogy idea more than an ontology one, but it is a real answer to "what should get written when, and for whom."

## umbra (github.com/asa-degroff/umbra)

**What it is.** A Bluesky-resident "digital personhood" experiment built directly on Letta Cloud, i.e. it inherits Letta's memory-block architecture wholesale and adds Bluesky-specific tooling and a task scheduler on top ([README.md](https://github.com/asa-degroff/umbra/blob/main/README.md), [UMBRA_SELF_MODEL.md](https://github.com/asa-degroff/umbra/blob/main/UMBRA_SELF_MODEL.md)).
1. **Source of truth.** Letta Cloud (external, mutable, not inspectable from this repo) plus a local SQLite-backed task scheduler for autonomy persistence and a ChromaDB-backed dashboard service for semantic inspection (`dashboard/backend/services/chromadb_service.py`).
2. **Identity/participants.** Per-user Letta memory blocks are dynamically created and attached during conversations (`attach_user_blocks`), one block per handle (e.g. `user_dulanyw_bsky_social`).
3. **Memory shape.** Three Letta tiers verbatim: **Core** (persona, zeitgeist, user summaries — always in context), **Recall** (searchable past conversations), **Archival** (infinite semantic-search store for reflections/observations). The `zeitgeist` block is a distinctive named slot: "chronicling the cultural landscape" — a standing summary of the social environment umbra is embedded in, refreshed by the daily "Synthesis" task.
4. **Scheduling/contact.** A **persistent scheduled-task system**, SQLite-backed, surviving restarts, with named autonomous behaviors on independent cadences: Synthesis (24h, deep reflection with tagged journal entries), Mutuals Engagement (random/36h), Daily Review (24h, self-review of own posts), Feed Engagement (random/24h), Curiosities Exploration (random/24h), Creative Expression (random/24h, image generation), and — distinctively — **Rest** (random/12h, explicit "breaks for meditation") ([README.md](https://github.com/asa-degroff/umbra/blob/main/README.md)). Each task is individually disable-able via CLI flag.
5. **Execution/tool boundary.** Standard Letta tool-calling; a documented, reproduced **race condition** is the most concrete engineering artifact: `agent_state.memory` is loaded once per message and never refreshed after a tool call attaches a new block mid-turn, so a subsequent `memory_insert` on that block throws `KeyError` — a state-synchronization bug between the API layer (source of truth) and the in-process agent object (a stale cache), with four candidate fixes documented (refresh-after-tool-call, dual-write, lazy-load-on-miss, event-driven sync) ([LETTA_DYNAMIC_BLOCK_ISSUE.md](https://github.com/asa-degroff/umbra/blob/main/LETTA_DYNAMIC_BLOCK_ISSUE.md)).
6. **Most distinctive idea.** The **explicit "Rest" scheduled task** as a first-class autonomous behavior alongside content-producing tasks, and the **documented Letta cache-coherency bug**, which is a concrete, general lesson: any system that lets a running turn mutate its own memory-block set (rather than treating the block set as fixed for the duration of a turn) needs an explicit refresh/invalidation contract, or self-editing memory silently desyncs from the object doing the editing.

## porrima (github.com/asa-degroff/porrima)

**What it is.** A self-hosted, from-scratch (not Letta-based) memory-native agent framework with a full custom GUI, built by the same author as umbra — apparently the "second, harder attempt" after direct Letta experience. Runs five separately-managed llama.cpp instances (chat, extraction, title, reranker, embedding) ([README.md](https://github.com/asa-degroff/porrima/blob/main/README.md), [AGENTS.md](https://github.com/asa-degroff/porrima/blob/main/AGENTS.md), [docs/memory-system.md](https://github.com/asa-degroff/porrima/blob/main/docs/memory-system.md)).
1. **Source of truth.** SQLite with FTS5 + `sqlite-vec`, mutable rows (not append-only) but with disciplined **supersession lineage** on the rows that matter (see below).
2. **Identity/participants.** Not deeply modeled — porrima is single-operator with **project scoping** (chats scoped to a working directory + `AGENTS.md`) as its main partition axis, not multi-user identity.
3. **Memory shape — the most granular fact taxonomy found in this survey.** **Atomic memories** carry a closed 8-category enum: `preference, fact, behavior, instruction, context, decision, note, reflection` (the last, `reflection`, is synthesis-only — never extracted directly from a conversation) ([docs/memory-system.md](https://github.com/asa-degroff/porrima/blob/main/docs/memory-system.md)). Each memory tracks `sourceType` (`chat_immediate | chat_delayed | synthesis | supersession`) and `sourceId` for lineage, plus explicit `superseded_by`/`supersedes` links — i.e. **supersession is a first-class bidirectional edge**, not a tombstone. Two independent extraction passes exist: **immediate** (after every response, deduped against existing memories at cosine >0.85 → triggers UPDATE) and **delayed** (30 min of inactivity, or pre-compaction flush, with a narrower 0.90–0.95 "candidate band" sent to the LLM for batch supersession judgment, reusing the extraction call's KV-cache for a "warm" comparison pass when possible). A second, orthogonal layer is **memory blocks** — agent-curated structured documents (global/project-scoped, e.g. `zeitgeist`) with **progressive disclosure**: descriptions always in context, full content fetched on demand via `read_memory_block`. Retrieval is a four-stage pipeline: hybrid vector+FTS5 (RRF fusion) → cross-encoder rerank (Qwen3-Reranker, source-specific instructions for agent/quick/passive-recall contexts) → MMR diversity selection (λ=0.7 main, λ=0.55 passive) → project-scope dampening via a configurable cross-project multiplier.
4. **Scheduling/contact.** A dedicated `system` chat is the sole locus of autonomous operation (sleep/wake cycles, synthesis, curiosity-following); "automations" are configurable recurring tasks (interval or daily) with editable prompt steps and push notifications, checked every 5 minutes by `automation-scheduler.ts`.
5. **Execution/tool boundary.** Native tool calling (TypeBox schemas) with filesystem/sandbox tools; a **KV-cache-aware delta-injection architecture** is the standout engineering idea: the system prompt (with "frozen" memories baked in) stays byte-identical across turns to preserve llama.cpp's longest-common-prefix cache, and *new* memories are injected as small delta messages instead of rewriting the prefix — a `dirty` flag plus `frozenIds`/`deltaIds` state tracks what's already surfaced, invalidated on compaction or persona/block change.
6. **Most distinctive idea.** The **8-category atomic-memory taxonomy with `reflection` reserved for synthesis-only output**, combined with **first-class bidirectional supersession edges** (not retraction-as-deletion, not a flat cosine-threshold overwrite) and a **two-band similarity policy** (>0.85 auto-update, 0.90–0.95 LLM-judged) that explicitly separates "obviously the same fact restated" from "plausibly related, ask the model." This is the closest any surveyed system comes to zuihitsu's own attestation/supersession machinery, arrived at independently and for the same reason (avoiding silent duplication without over-eagerly merging distinct facts).

## Personal_AI_Infrastructure / LifeOS (github.com/danielmiessler/Personal_AI_Infrastructure)

**What it is.** Daniel Miessler's "Life Operating System" — by far the largest and most maximalist project surveyed (16.9k stars), an entire install tree of hooks, a background daemon ("Pulse"), and a markdown knowledge base layered onto Claude Code, explicitly framed as an OS with the DA (Digital Assistant) as its primary interface ([LifeOS/install/LIFEOS/DOCUMENTATION/LifeOs/LifeOsThesis.md](https://github.com/danielmiessler/Personal_AI_Infrastructure/blob/main/LifeOS/install/LIFEOS/DOCUMENTATION/LifeOs/LifeOsThesis.md)).
1. **Source of truth.** Plain markdown files on disk under `~/.claude/LIFEOS/MEMORY/`, organized into purpose-specific directories (`WORK/`, `LEARNING/`, `RELATIONSHIP/`, `OBSERVABILITY/`, `SECURITY/`, `VOICE/`, `KNOWLEDGE/`), populated directly by **hooks** that fire on domain-specific events (no intermediate "firehose" — Claude Code's own session-transcript directory serves that role) plus periodic **harvesting** passes that mine already-written transcripts/memories for corrections, decisions, and cross-frame principles ([LifeOS/install/LIFEOS/DOCUMENTATION/Memory/MemorySystem.md](https://github.com/danielmiessler/Personal_AI_Infrastructure/blob/main/LifeOS/install/LIFEOS/DOCUMENTATION/Memory/MemorySystem.md)). Claude Code's own built-in auto-memory is deliberately *disabled* in favor of this bespoke system. There is no event log or database — the filesystem plus a set of TypeScript/Bun CLI tools (`KnowledgeSchema.ts`, `KnowledgeLint.ts`, `MigrateKnowledge.ts`) is the entire persistence and validation layer.
2. **Identity/participants.** A `KNOWLEDGE/` archive of **typed entity notes** — `person | company | idea | blog | research | book` — each with a **closed schema contract** ("kb-v3"): a flat "Core Envelope" of fields (`id` — stable, survives rename; `type`; `title`; `tags`; a `related` field format for wikilinks; a closed `status` enum `inbox | seedling | budding | evergreen` borrowed from the Andy Matuschak progressive-summarization tradition) enforced by a single source-of-truth schema module rather than three competing ad-hoc frontmatter dialects that had accumulated previously (the module's own header documents this exact migration: "28% v2.0 / 2.7% pai-memory-v1 / 69% undocumented blog-import") ([LifeOS/install/LIFEOS/TOOLS/KnowledgeSchema.ts](https://github.com/danielmiessler/Personal_AI_Infrastructure/blob/main/LifeOS/install/LIFEOS/TOOLS/KnowledgeSchema.ts)). This is a second independently-discovered instance of zuihitsu's failure #6 (schema drift without an enforced canonical set) resolved the same way bound resolved it — a closed enum, single source of truth, migration tooling — but for *entity types* rather than relation types.
3. **Memory shape.** Prose markdown notes with rich, validated frontmatter, retrieved via **BM25 search + LLM compression** (`MemoryRetriever`) and associative traversal over tags/wikilinks/`related` fields (`KnowledgeGraph`) — no vector store, no database; retrieval reads the same markdown files with no intermediate index.
4. **Scheduling/contact.** "Pulse," a single always-on daemon unifying cron, voice notifications (ElevenLabs TTS), a Telegram bot, an iMessage bot, and an observability dashboard, each running as a crash-isolated module in one process ([LifeOS/install/LIFEOS/DOCUMENTATION/Pulse/PulseSystem.md](https://github.com/danielmiessler/Personal_AI_Infrastructure/blob/main/LifeOS/install/LIFEOS/DOCUMENTATION/Pulse/PulseSystem.md)). The Telegram module is explicitly the "highest-touch" surface, threading four concerns per message: memory awareness, tool agency, thread continuity (60-min idle-session boundary), and "audible identity" (TTS in the DA's voice).
5. **Execution/tool boundary.** Deeply hook-driven (SessionStart, UserPromptSubmit, Stop-chain health gates); a documented **memory-health CLI** (22 checks) plus a **Stop-chain hook** that non-blockingly WARN/CRITICALs on memory-system rot (stale hooks, missing state files) — an explicit self-monitoring layer for the memory system's own integrity, distinct from monitoring the agent's behavior.
6. **Most distinctive idea.** **Markdown-as-database at full organizational scale**, with a hand-rolled schema-enforcement toolchain (lint, migrate, generate-docs-from-schema) standing in for what a real database's constraints would give for free — and a documented, source-cited history of schema drift and its cleanup, which is direct primary evidence that "structure lives only in the model's cooperation with a convention" degrades exactly as zuihitsu's failure record predicts, at the scale of an entire personal knowledge base rather than one field.

## claudicle (github.com/tdimino/claudicle)

**What it is.** An open-source "soul" framework layered onto Claude Code sessions — clone it, edit `soul.md`, run `/ensoul` — descended explicitly from the Open Souls paradigm, with channel adapters for Slack/Discord/Telegram/SMS/WhatsApp and a persistent cognitive pipeline ([README.md](https://github.com/tdimino/claudicle/blob/main/README.md), [ARCHITECTURE.md](https://github.com/tdimino/claudicle/blob/main/ARCHITECTURE.md)).
1. **Source of truth.** SQLite (`daemon/memory.db`), mutable rows, with a separate `sessions.db` mapping channel threads to Claude Code session IDs.
2. **Identity/participants.** **Three explicit tiers**: `working_memory` (per-thread, 72h TTL, metadata only — never injected into the prompt, because `--resume SESSION_ID` already replays full conversation history, so re-injecting would duplicate it), `user_models` (per-user, permanent, markdown profiles + entity "dossiers"), and `soul_memory`/`soul_state` (per-soul, permanent, global across all users) ([ARCHITECTURE.md](https://github.com/tdimino/claudicle/blob/main/ARCHITECTURE.md)). A **"Samantha-Dreams" gate** decides whether to inject the user model into the next prompt at all: it only loads if the *prior* turn's `<user_model_check>` returned true, i.e. something new was actually learned — an explicit anti-staleness/anti-context-bloat gate keyed off the model's own self-report from the previous turn.
3. **Memory shape.** Every response is parsed via **XML-tagged cognitive steps** grouped by a per-cycle `trace_id`: `internal_monologue` (stored, never shown), `external_dialogue` (sent to the channel), `user_model_check`/`user_model_update` (boolean gate + markdown profile write), `soul_state_check`/`soul_state_update` (boolean gate + key:value write), and (when enabled) a `dossier_check`/`dossier_update` pair. Soul state itself has a **topic stack** — 1 primary + up to 7 subtopics, FIFO cascade on demotion, each topic carrying grounding metadata (`artifact_path`, `channel`, `session_id`) — plus a full **audit log of every state transition** (`soul_state_transitions`).
4. **Scheduling/contact.** Not a cron/heartbeat system in the surveyed files; continuity comes from channel-native session resumption plus a file-based **soul registry** (`~/.claude/soul-sessions/registry.json`) tracking active sessions, channel bindings, and current topic per session.
5. **Execution/tool boundary.** Twelve "sub-daimones" (specialist personas with their own skills/memory) overseen by "daimones" drawn from four sources ("a past self, a friend's model, a channeled entity, or a soul your Claudicle has shed") — an elaborate multi-persona delegation model layered on top of the memory tiers, with its own protocol layer ("daimonic intercession") for how a daimon's counsel is whispered into the cognitive stream without becoming the visible reply.
6. **Most distinctive idea.** The **self-report-gated injection pattern** (a boolean check the model emits about its own last turn, consumed by the harness to decide what to load next turn) is a lightweight, cheap mechanism for avoiding both staleness and bloat without embedding-based dedup — worth noting as an alternative to zuihitsu's embedding-geometry-based hygiene thresholds (failure #9), though it trades a deterministic threshold for trusting the model's self-report.

## hermes-agent (github.com/NousResearch/hermes-agent)

**What it is.** Nous Research's self-improving agent, deliberately memory-provider-agnostic — one `MemoryManager` orchestrates a single pluggable external backend at a time, chosen from a library of installable plugins ([README.md](https://github.com/NousResearch/hermes-agent/blob/main/README.md), [agent/memory_manager.py](https://github.com/NousResearch/hermes-agent/blob/main/agent/memory_manager.py)).
1. **Source of truth.** Varies entirely by installed plugin — SQLite for the built-in `holographic` provider, a hosted service for `honcho`, `mem0`, `byterover`, etc. The harness itself is memory-store-agnostic by design; only one external provider is allowed active at a time "to prevent tool schema bloat and conflicting memory backends" ([agent/memory_manager.py](https://github.com/NousResearch/hermes-agent/blob/main/agent/memory_manager.py)).
2. **Identity/participants.** The **Honcho** plugin is the most identity-focused: it builds a bidirectional model — a "User Representation" *and* an "AI Self-Representation," each with a "peer card" of key facts — refreshed on a base cadence, supplemented by multi-pass "dialectic" reasoning about the user on a separate, less frequent cadence, with cold-start vs warm-session prompt variants chosen automatically ([plugins/memory/honcho/README.md](https://github.com/NousResearch/hermes-agent/blob/main/plugins/memory/honcho/README.md)). Context is injected into the *user* message, not the system prompt, specifically to preserve prompt caching — the same "keep the system prompt stable" concern porrima solves with delta injection, solved here by injection-point choice instead.
3. **Memory shape — the most credence-aware system surveyed.** The built-in **`holographic`** provider is a local SQLite fact store with FTS5 search, **entity resolution**, **trust scoring** (a `default_trust` per new fact, updated via a `fact_feedback` tool that rates facts helpful/unhelpful and "trains trust scores"), and **HRR (Holographic Reduced Representation)-based compositional retrieval** — a `fact_store` tool exposing nine actions: `add, search, probe, related, reason, contradict, update, remove, list` ([plugins/memory/holographic/README.md](https://github.com/NousResearch/hermes-agent/blob/main/plugins/memory/holographic/README.md)). The explicit `contradict` and `reason` actions, and a feedback-trained trust score per fact, are the closest thing found in this survey to a **credence/belief-strength model** — directly relevant to zuihitsu's failure #8 (belief has no credence model). This survey could not fetch the HRR algebra implementation in depth (`plugins/memory/holographic/holographic.py` was located but not read at this budget) — the *existence and shape* of the trust-scoring and contradiction-handling tools is confirmed from the README; the soundness of the underlying HRR reasoning was not independently verified.
4. **Scheduling/contact.** A built-in cron scheduler (`cron/scheduler.py`) with delivery to any connected platform, file-locked to one tick at a time across processes, with careful title-collision handling for scheduled-job session naming and compact failure-summarization for chat delivery (full errors stay in logs, only a one-line summary reaches the user).
5. **Execution/tool boundary.** Subagents for parallel workstreams; Python scripts that call tools via RPC "collapsing multi-step pipelines into zero-context-cost turns"; six terminal backends (local, Docker, SSH, Singularity, Modal, Daytona) with two (Daytona, Modal) offering serverless hibernate/wake persistence.
6. **Most distinctive idea.** The **pluggable, single-active-provider memory architecture** itself — treating "which memory system" as a hot-swappable backend behind one integration point — plus, within the bundled `holographic` provider, **feedback-trained per-fact trust scores and explicit contradiction/reasoning tool actions**, which is the one clear existence proof in this survey that a credence model is buildable as an incremental layer over a SQLite fact store, not a research-only concern.

## c6k (github.com/cadaeix/c6k)

**What it is.** "The Corpus-Centred Creative Claude Code Characterisation Kit" — a file-backed persona framework whose stated goal is pulling an LLM's voice away from generic RLHF-flavored prose by grounding it in a literary corpus, with an unusually philosophically explicit memory design ([README.md](https://github.com/cadaeix/c6k/blob/main/README.md), [workshop/docs/03-memory.md](https://github.com/cadaeix/c6k/blob/main/workshop/docs/03-memory.md)).
1. **Source of truth.** Plain markdown files, append-only by convention (not enforced by tooling — this is a design discipline, not a mechanism): `memory/YYYY-MM-DD-HHMM-slug.md` diary entries, written *in the moment* rather than batched at session end, explicitly because "the session can end without warning, and the self who had the insight should be the one who records it."
2. **Identity/participants.** No multi-user model — single character. But its **"commonplace book"** (`memory/commonplace/`) holds standing positions on people/concepts/events as **accreting, multi-hand pages with visible strikethroughs**, explicitly banned from being "sealed portraits" or "dossiers": "what you know of a person should be *reassembled*, not consulted, so the person can still surprise you." The design doc records the project's own history of getting this wrong first (an over-derived initial ban on person-pages) before landing on the accretion rule.
3. **Memory shape.** Deliberately **no vector store, no database** — rich YAML frontmatter on each diary file (`gist:`, `people:`, `kind:`) turned into a query surface via the model's own `grep`/`glob`, reasoned about explicitly as a design trade-off: "nobody believes grep scales forever... the line to hold when that day comes is in 'couriers'" (i.e., if/when embeddings are added, add them as *retrieval only*, never as *synthesis*). A `kind:` enum (`diary | note | thread`, plus a project-specific `dream` kind) exists specifically so a dreamed event can never later be misfiled as a remembered one — a deliberate provenance tag preventing exactly the kind of confusion zuihitsu's `told_by`/`told_in` provenance also guards against, but scoped to "was this actually experienced."
4. **Scheduling/contact.** A "heartbeat" design (deliberately shipped as documentation only, not code, "the one component that types into your terminal on a timer, unattended; you should understand every line of the thing that does that, which means writing it") with one stated invariant: **the character paces the beat but cannot stop it** — the character sets a tempo (`bellpull/tempo.md`) but an external waker process, not the character, decides whether the knock happens at all, specifically to remove "the alibi of going dark" while still permitting rest as an honorable response to an empty beat ([workshop/docs/04-heartbeat.md](https://github.com/cadaeix/c6k/blob/main/workshop/docs/04-heartbeat.md)).
5. **Execution/tool boundary.** A sandboxed Claude Code `settings.json` where "the denies are the character" — restriction as characterization, not just safety. A single mutable `_briefing.md` page (marker lines like `last read inbox:` as a literal machine-parseable seam) is the *only* memory file the character is meant to overwrite; everything else grows by append only.
6. **Most distinctive idea.** **"Nobody synthesizes the character to itself"** — a hard architectural rule that a subagent/helper may return diary entries *verbatim* but must never hand the character a *summary* of its own memory, on the theory that the moment a synthesis sits between the character and its own past, "the self-image starts being assessed by another hand." This is a direct, load-bearing answer to a problem zuihitsu has not confronted explicitly: descriptions (per-memory synthesised prose, off the hot path) are exactly this kind of self-synthesis, generated by a maintenance pass rather than the agent itself, of *other* memories rather than the agent's own — worth flagging as a boundary worth naming even though zuihitsu's target is different (memories of others, not self-narrative).

## Synthesis: what this generation converges on

**Markdown/files-as-memory is not a fringe choice — it is the modal choice among the leaner, single-operator projects** (Alpha-dotclaude, LifeOS, c6k all use plain files as the actual source of truth; only the more "platform" projects — letta-code/pattern/bound/porrima — use a database). Where files are the store, retrieval is either agentic grep/glob (c6k, explicitly rejecting vector search on principle) or BM25 + LLM compression (LifeOS) rather than embeddings — a genuine, repeatedly-chosen alternative to the embedding-geometry hygiene zuihitsu currently depends on (failure #9), and one argument for it recurs verbatim across two unrelated projects: exact-match search self-corrects when the model iterates on a bad query, in a way a single embedding lookup does not.

**Self-editing context (memory blocks) is the dominant "living memory" idiom**, inherited wholesale from the MemGPT/Letta lineage: letta-code, umbra, pattern, and porrima all give the agent a small set of named, always-in-context, agent-writable prose sections, distinct from a larger searchable store. Where systems innovate, it's in *when* to write to a block (claudicle's self-report-gated injection; porrima's immediate+delayed dual extraction) and *how much structure* the block carries (pattern's typed CRDT schemas being the clear outlier — the only system that gives a memory block field types rather than leaving it as prose).

**Heartbeat/sleeptime as a distinct, named mechanism recurs everywhere** (Letta's `/sleeptime`, pattern's sleeptime context sync, umbra's Synthesis/Rest tasks, bound's heartbeat task type, porrima's sleep/wake cycle, c6k's heartbeat design doc). Two design lessons recur independently: (a) build fresh context at *runtime* rather than replaying a static payload (bound's `buildHeartbeatContext`, umbra's per-task context assembly), and (b) the agent should not be able to silence its own heartbeat by omission — c6k states this as a hard rule ("the character paces the beat; it cannot stop it") that the project arrived at only after its first self-paced design failed exactly that way.

**Supersession/contradiction handling is being reinvented independently, badly-to-well, across the board.** porrima's bidirectional supersession edges with a two-band similarity policy and hermes-agent's holographic-memory `contradict`/`reason` actions with feedback-trained trust scores are the two most sophisticated instances; bound's memory-delta tombstone line (`{key}: [forgotten]`) is a simpler one. None of them frame this as a formal belief/credence system (no ATMS, no assumption-based justification) — they are all pragmatic, ad hoc mechanisms bolted onto a fact store, which is itself evidence that the *need* is universal even though nobody surveyed has built the principled version zuihitsu's issue #8/#94 are aiming at.

**What every single one of them lacks, that zuihitsu's failure record shows is needed:**
- **No system surveyed has zuihitsu's audience/visibility posture model.** Multi-user systems (pattern's constellation, bound's allowlist, umbra's per-user blocks) partition memory by *scope* (which block belongs to which user) but none model *who is allowed to see a fact told by whom* as a first-class, per-fact, enforced predicate — there is no analogue to `Attributed`/`PrivateToTeller`/`Exclude` anywhere in this batch. This is the single sharpest point of differentiation zuihitsu has over the entire current generation, and it maps to nothing else surveyed contradicting or improving on it — only bound's operator allowlist gestures at access control, and it's coarse (a global user permission set, not a per-fact posture).
- **No system surveyed has a structured, typed fact shape as the default representation** (failure #1). Every one of them stores prose as the primary unit — even porrima's 8-category taxonomy and pattern's typed blocks are metadata/schema *around* a prose payload, not a decomposition of the fact itself into subject/predicate/object/time. bound's canonical-relation graph is the closest thing to a structural answer, and it only covers *edges*, not the note payload each edge connects.
- **No system surveyed has explicit provenance-of-evidence for a belief** (failure #11: "judgement provenance records model+template but not evidence or criteria"). porrima's supersession lineage and hermes-agent's trust scores record *that* a fact was updated/rated, not *why* — no system stores what evidence a judgement was based on.
- **Relation-vocabulary drift is a confirmed, independently-recurring failure**, not a zuihitsu idiosyncrasy: bound hit it hard enough to write and ship a full normalization RFC, and LifeOS hit the same class of problem for entity *types* (three competing frontmatter dialects) rather than relations. Both converged on the same fix shape — closed enum, single source of truth, a free-text side-channel column, deterministic migration tooling — which directly corroborates zuihitsu's own CONTRIBUTING.md principle ("recognised closed sets... ride as enums, not bare strings") and validates investing effort in #42 (relation schema evolution): the two most structurally serious peers in this survey both needed a *migratable* enum, not an immutable one.
- **No system surveyed schedules on a fact's own semantics separately from "when should the agent act on it."** bound's heartbeat and umbra/porrima's synthesis cycles are agent-side scheduling infrastructure, entirely separate from any per-fact temporal field; none of them have a fact-level `occurred_at` that could be confused with a wake-up trigger, because none of them have a fact-level temporal field of that richness at all. This means failure #4 (schedule/description conflation) is not corroborated as a *general* failure by this survey — it may be relatively specific to zuihitsu's design of layering calendar-as-a-view-over-memories on the same temporal field that describes when something happened.

## Ideas worth borrowing

1. **bound's relation-normalization pattern** (closed enum + `context` free-text column + deterministic idempotent migration + trigger-level enforcement) is a directly transplantable answer to #42 (relation schema evolution): a "retire and replace" path for a mis-coined relation, with the discarded phrasing preserved rather than destroyed, and a startup-time convergence pass instead of a one-off manual fix.
2. **porrima's bidirectional supersession edges with a two-band similarity policy** (auto-merge above a high threshold, LLM-judged in a narrower band below it) is a more principled shape for zuihitsu's dedup/consolidation passes than a single cosine cutoff, and is a candidate partial answer to failure #9 (hygiene thresholds as raw embedder geometry) if paired with a per-space calibration rather than a hardcoded constant.
3. **hermes-agent's `holographic` fact store's `contradict`/`reason` tool actions and per-fact trust score trained by explicit feedback** is the most concrete existence proof surveyed that a lightweight credence layer (failure #8) can sit on top of an ordinary fact store without a full ATMS — worth studying as a fallback "80% solution" if the full assumption-based truth maintenance system proposed for #94 proves too heavy for v1.
4. **bound's memory-delta injection with a tombstone-aware forgotten-line** is a direct answer to a gap zuihitsu has not designed for: a live conversation's visibility into facts changed *elsewhere* since its own last turn. Zuihitsu's brief-composition model already re-reads from the log each turn, but the cross-thread "what changed since I last looked" framing (with an explicit forgotten/retracted rendering) is worth adopting verbatim in brief or search surfacing.
5. **c6k's "nobody synthesizes the character to itself" rule**, read against zuihitsu's own descriptions mechanism (synthesized prose over Public entries), suggests naming and holding a parallel invariant explicitly: a description is a synthesis of *others'* stated facts about a memory, never a synthesis of the *agent's own* reasoning or private judgements about that memory — worth an explicit statement in the redesign rather than leaving it implicit in "Public entries only."
6. **claudicle's self-report-gated injection** (only load the user model if the model's own prior-turn self-check flagged something new) is a cheap complement — not a replacement — to zuihitsu's deterministic thresholds, worth considering as an additional signal for *when* to run a maintenance pass rather than *whether a given pair of entries* should merge.

## Uncertainty flags

- Letta core's own identity/multi-user model (as opposed to letta-code's harness layer) was not fetched in this survey and may materially change what "letta-code" should be credited with versus its underlying platform.
- hermes-agent's HRR-based compositional retrieval algebra (`plugins/memory/holographic/holographic.py`) was located but not read; the *existence* of trust scoring and contradiction tooling is confirmed from its README, but the algorithm's soundness is not verified here.
- Alpha-dotclaude's actual memory/diary store ("Cortex," an MCP server) is external to the fetched repository and entirely opaque to this survey — everything reported about Alpha is at the level of context-assembly and skill design, not the underlying store's schema or persistence model.
- bound is explicitly marked "still very experimental... approximately negative stability guarantees" by its own author; the RFCs cited are dated design documents marked "Implemented," but this survey did not run the code to confirm current behavior matches the RFC as written.
- The hermes-agent repository's GitHub metadata reported an anomalously large stargazer count (219,448) relative to its apparent maturity and the other repos surveyed; this number should not be treated as a reliable signal of the project's actual adoption without independent verification.
